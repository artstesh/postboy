# Migrating from 3.3 to 3.4

Version 3.4 is a tooling and packaging release: no message bus API changed, and no
application-level migration is expected. This note explains what to check so the
upgrade is a non-event.

## What 3.4 changed

- The package is now built with dual output: ESM (`lib/index.mjs`), CommonJS
  (`lib/index.cjs`), TypeScript declarations, and source maps.
- `package.json` exposes an explicit `exports` map, so module resolution depends on
  the `import`/`require` condition instead of the `main` field alone.
- Internally the project moved from TSLint to ESLint and gained dedicated
  `typecheck`, `build`, and `pack:check` scripts. This affects contributors only.

The deprecations introduced in 3.3 (direct `PostboyService` mutation methods such as
`addMiddleware` or `lock`) still work in 3.4. They are removed in 3.5 — see
[Migrating from 3.4 to 3.5](3-4-to-3-5.md).

## What to check

Standard `rxjs`-based consumers need nothing: the public API surface of the bus is
unchanged.

If you consume the package from a custom build setup (monorepo bundler config,
Jest module mapper, or a Node.js `require`), make sure your environment resolves
the package through its `exports` map:

```json
{
  "import": "./lib/index.mjs",
  "require": "./lib/index.cjs",
  "types": "./lib/index.d.ts"
}
```

- TypeScript should be at least 4.7 for `exports`-aware resolution (`moduleResolution`
  `node16`/`nodenext` recommended; classic `node10` resolution falls back to `main`,
  which points at the CommonJS build).
- Jest with `ts-jest` may need `moduleNameMapper` only if it ignores `exports`;
  the default configuration resolves the CommonJS build.
