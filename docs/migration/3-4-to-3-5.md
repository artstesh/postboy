# Migrating from 3.4 to 3.5

Version 3.5 is a **source-breaking** release. It replaces the single-hook middleware
with a staged abstract class, removes the remaining direct mutation methods of
`PostboyService` in favor of infrastructure messages, and turns throw-to-block into
a structured cancellation. Middleware written for 3.4 does not compile against 3.5,
and neither does code that called the removed methods.

Three areas to work through, in the order you will hit them at compile time:

1. [Replace removed service methods](#replace-removed-service-methods)
2. [Rewrite custom middleware](#rewrite-custom-middleware)
3. [Replace throw-to-block with `Interrupt`](#replace-throw-to-block-with-interrupt)

Coming from 3.3? Everything below applies to you as well: the methods deprecated in
3.3 are the ones removed in 3.5.

## Replace removed service methods

`lock`, `unlock`, `addMiddleware`, `removeMiddleware`, `addNamespace`,
`eliminateNamespace`, and `unregister` are gone. Infrastructure messages are the only
way to mutate the bus now:

| Removed call (3.4) | Replacement (3.5) |
|---|---|
| `postboy.addMiddleware(mw)` | `postboy.exec(new AddMiddleware(mw))` |
| `postboy.removeMiddleware(mw)` | `postboy.exec(new RemoveMiddleware(mw))` — also calls `mw.dispose()` |
| `postboy.lock(MyMessage)` | `postboy.exec(new LockMessage(MyMessage))` |
| `postboy.unlock(MyMessage)` | `postboy.exec(new UnlockMessage(MyMessage))` |
| `postboy.unregister(MyMessage.ID)` | `postboy.exec(new DisconnectMessage(MyMessage.ID))` |
| `postboy.addNamespace('feature')` | `postboy.exec(new AddNamespace('feature'))` |
| `postboy.eliminateNamespace('feature')` | `postboy.exec(new EliminateNamespace('feature'))` |

A locked type can still be registered but is not published until unlocked — the same
semantics `lock()`/`unlock()` had.

The deprecated registration methods (`record`, `recordWithPipe`, `recordExecutor`,
`recordHandler`) still compile in 3.5, but they are on the same removal track. Switch
them in the same pass:

```typescript
// 3.4 (deprecated already, removed soon)
postboy.record(MyMessage, subject);
postboy.recordWithPipe(MyMessage, subject, (sub) => sub.pipe(share()));
postboy.recordExecutor(MyExecutor, (e) => handler(e));
postboy.recordHandler(MyExecutor, myHandler);

// 3.5
postboy.exec(new ConnectMessage(MyMessage, subject));
postboy.exec(new ConnectMessage(MyMessage, subject, (sub) => sub.pipe(share())));
postboy.exec(new ConnectExecutor(MyExecutor, (e) => handler(e)));
postboy.exec(new ConnectHandler(MyExecutor, myHandler));
```

Registrator classes (`PostboyAbstractRegistrator`) already use the messages
internally — custom registrators need no changes.

## Rewrite custom middleware

The 3.4 contract was one interface with a single hook. In 3.5 middleware is an
abstract class with stage-aware hooks:

| 3.4 | 3.5 |
|---|---|
| `interface PostboyMiddleware { handle(message): void }` | abstract class with `canHandle`, `before`, `after`, `dispose` |
| One `handle` hook for every operation | Hooks per stage: `MiddlewareStage.Publish` (`fire`), `Callback` (`fireCallback`), `Execute` (`exec`) |
| No filter — every middleware saw every message | `canHandle(context)` scopes by stage and message |
| No visibility into outcomes | `after(context, result?)` receives the executor's return value on `Execute` |

A typical 3.4 implementation:

```typescript
// 3.4
class LoggingMiddleware implements PostboyMiddleware {
  handle(message: PostboyMessage): void {
    console.log('message', message.id);
  }
}

postboy.addMiddleware(new LoggingMiddleware());
```

Split the hook by responsibility — gating to `before`, observation to `after`,
filtering to `canHandle`:

```typescript
// 3.5
import {
  PostboyMiddleware, PipelineContext, MiddlewareDecision,
  MiddlewareDecisionType, MiddlewareStage, AddMiddleware,
} from '@artstesh/postboy';

class LoggingMiddleware extends PostboyMiddleware {
  canHandle(context: PipelineContext): boolean {
    return context.stage === MiddlewareStage.Execute;
  }

  before(context: PipelineContext): MiddlewareDecision {
    console.log('attempt', context.message.id);
    return { type: MiddlewareDecisionType.Continue };
  }

  after(context: PipelineContext, result?: unknown): void {
    console.log('done', context.message.id, result);
  }
}

postboy.exec(new AddMiddleware(new LoggingMiddleware()));
```

Notes that save debugging time:

- Middleware hooks now also see infrastructure messages (`AddMiddleware`,
  `ConnectMessage`, …) — they are executors on the `Execute` stage. Filter with
  `canHandle` if your middleware must not react to them.
- Give guards a name via `super('ReadonlyGuard')`: the `CancelError` reason is
  generated from it.
- Implement `dispose()` for anything the middleware allocates; `RemoveMiddleware`
  and `postboy.dispose()` call it.
- Assume `after` can be skipped: any middleware may interrupt the operation first.

## Replace throw-to-block with `Interrupt`

In 3.4 the only way to stop an operation from middleware was throwing, and callers
saw an ordinary exception. In 3.5 a block is a decision returned from `before`, and
the bus converts it into a structured `CancelError`:

```typescript
// 3.4
handle(message: PostboyMessage): void {
  if (this.readonly) throw new Error('Readonly mode');
}

// 3.5
before(_context: PipelineContext): MiddlewareDecision {
  return this.readonly
    ? { type: MiddlewareDecisionType.Interrupt }
    : { type: MiddlewareDecisionType.Continue };
}
```

Call sites that expect blocking now catch a `CancelError` instead of parsing message
text:

```typescript
import { CancelError } from '@artstesh/postboy';

try {
  postboy.exec(new DeleteUserExecutor(userId));
} catch (e) {
  if (e instanceof CancelError || (e as Error).name === 'PostboyCancelError') {
    return; // blocked by policy — see e.details.middleware, .stage, .messageId
  }
  throw e;
}
```

## Migration checklist

- [ ] Replace every removed `PostboyService` call with the corresponding
      infrastructure message (table above).
- [ ] Replace the deprecated `record*` calls with `ConnectMessage` /
      `ConnectExecutor` / `ConnectHandler`.
- [ ] Split each `handle` implementation: policy checks into `before`, logging and
      metrics into `after`, scoping into `canHandle`.
- [ ] Convert throw-to-block guards into `Interrupt` decisions; update call sites
      to catch `CancelError` and read `CancelDetails`.
- [ ] Implement `dispose()` where the middleware allocates resources.
- [ ] Update tests: assert on `CancelError.details` instead of thrown message
      strings, and remove middleware between tests to avoid leakage.
